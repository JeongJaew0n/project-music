# glossary

이 프로젝트 안에서만 통하는 도메인 용어를 정의한다. **새로 합류한 사람(과 AI)이
코드를 읽기 전에 먼저 읽는 문서**다.

용어가 흔들리면 코드도 흔들린다. 같은 것을 어디서는 `order`, 어디서는 `purchase`,
어디서는 `transaction` 이라 부르기 시작하면 그때부터 대화도 코드도 어긋난다.

## 무엇을 적나

**일반적인 뜻과 이 프로젝트에서의 뜻이 다른 것**만 적는다.

| 적는다 | 적지 않는다 |
|---|---|
| 이 프로젝트에서만 특별한 뜻인 말 | 일반 기술 용어 (`캐시`, `마이그레이션`) |
| 업계 용어인데 우리가 좁게/넓게 쓰는 말 | 코드를 보면 바로 아는 것 |
| 비슷한데 구분해서 써야 하는 두 말 | 한 번 쓰고 마는 말 |
| 팀이 합의한 약어 | |

판단 기준 — **"이 말을 처음 듣는 사람이 코드에서 만나면 헷갈릴까?"**

## 형식

용어 표를 이 파일에 유지한다. 설명이 길어지는 용어만 따로 파일로 뺀다.

| 용어 | 정의 | 비고 |
|---|---|---|
| (예) Draft | 사용자가 저장했지만 아직 게시하지 않은 글. `Post` 와 테이블이 같고 `status` 로 구분한다 | `Temp` 와 다름 — Temp 는 자동 저장본 |

## 규칙

- **코드의 이름과 일치시킨다.** 용어집에 `Draft` 라고 적었으면 코드에서도 `Draft` 다.
  적어놓고 코드에서 다르게 부르면 용어집이 거짓말이 된다.
- **이름을 바꾸면 용어집부터 고친다.** 코드만 바꾸고 두면 다음 사람이 낡은 정의를 믿는다.
- **혼동하기 쉬운 짝은 함께 적는다.** `Draft` 와 `Temp` 처럼 구분이 중요한 것은
  비고에 "무엇과 다른지" 를 쓴다. 정의만 있으면 경계가 안 보인다.

## 용어

| 용어 | 정의 | 비고 |
|---|---|---|
| FeatureGroup | 기능을 묶는 단위. 새 기능은 기존 FeatureGroup 에 넣을지 새로 만들지 먼저 정한다. 디렉터리·모듈 이름도 이 말을 따른다 | 화면 하나·파일 하나와 같은 말이 아니다 — 여러 화면과 모듈이 한 FeatureGroup 일 수 있다 |

| 작업실 (`studio/`) | 프로젝트 안의 데이터 폴더. 받은 원본과 작업 결과를 용도별 하위 폴더로 나눠 저장한다. git 제외. 경로는 `shared/paths.py` 의 `STUDIO_DIR` | 코드가 있는 프로젝트 폴더 전체와 다르다 |
| 받은 곡 (`studio/downloads/`) | 유튜브 등에서 받아 mp3 로 만든 **원본**. `DOWNLOADS_DIR`. `ytmp3`·`ytmp3-web` 의 기본 저장 위치 | 작업 결과와 섞지 않는다 — 원본은 다시 받을 수 있지만 결과는 아니다 |
| 작업 결과 (`studio/works/`) | 받은 곡을 AI 등으로 다듬거나 새로 만든 **결과물**. `WORKS_DIR`. 작업 종류마다 하위 폴더를 둔다 | 받은 곡과 다름 |
| 구간 자르기 (`songcut`) | 곡에서 시작~끝 구간만 떼어 새 파일로 저장하는 FeatureGroup. 원본은 건드리지 않는다 | 원본을 고치는 편집이 아니다 |
| 잘라낸 곡 (`studio/works/cuts/`) | 구간 자르기의 결과. 코드에서는 `Cut`, 폴더는 `CUTS_DIR` | 작업 결과의 한 종류 |
| 구간 | 곡 안의 시작~끝 시간 범위. 시간은 초(`83.5`) 또는 `분:초`(`1:23.5`). 끝이 음수면 곡 끝에서 거꾸로 센다 | |
| 소리 크기 (loudness) | `songcut info` 가 주는 초 단위 RMS 값(dBFS, 0 이 최대). AI 가 들을 수 없어 이것으로 자를 곳을 고른다 | 사람이 느끼는 음량(LUFS)과 다르다 |

다른 용어는 작업하며 채운다.
